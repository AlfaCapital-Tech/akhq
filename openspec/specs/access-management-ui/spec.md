# access-management-ui Specification

## Purpose
Пользовательский интерфейс самообслуживания доступов: единая страница Access Management (свои запросы, запрос доступа к префиксу, управление запросами и доступами для владельцев и суперадминов), кнопка запроса доступа на странице топика и пункт меню с числом ожидающих запросов. Видимость всех элементов определяется флагом `accessManagementEnabled` из `/api/auths`.

## Requirements

### Requirement: Флаг видимости из /api/auths
Ответ `GET /api/auths` MUST содержать поле `accessManagementEnabled`, равное значению `akhq.access-management.enabled`, а при `true` — список `requestableRoles` из пар `{name, label}`. UI SHALL загружать этот ответ при инициализации приложения, хранить в `sessionStorage` (`auths`) и при `accessManagementEnabled = false` SHALL NOT показывать пункт меню Access, регистрировать маршрут страницы, показывать кнопку Request Access и опрашивать счётчик ожидающих запросов.

#### Scenario: Функция выключена
- **WHEN** `/api/auths` возвращает `accessManagementEnabled: false`
- **THEN** в сайдбаре нет пункта Access, на странице топика нет кнопки Request Access, а переход на `/ui/{cluster}/access-management` не открывает страницу Access Management

#### Scenario: Функция включена
- **WHEN** `/api/auths` возвращает `accessManagementEnabled: true` и `requestableRoles`
- **THEN** все элементы Access Management видны любому залогиненному пользователю, а выпадающие списки ролей заполняются из `requestableRoles` в виде `name — label`

### Requirement: Пункт меню с числом ожидающих запросов
При включённой функции сайдбар SHALL содержать пункт «Access», ведущий на `/ui/{cluster}/access-management`. Рядом с ним MUST отображаться бейдж с числом из `GET /api/{cluster}/access-management/requests/pending/count`, если оно больше нуля. Счётчик SHALL обновляться при выборе кластера и каждые 30 секунд; ошибки запроса счётчика молча игнорируются.

#### Scenario: Владельцу пришли запросы
- **WHEN** у владельца префикса есть 3 ожидающих запроса в его зоне ответственности
- **THEN** на пункте Access отображается бейдж `3`, и он обновляется не позднее чем через 30 секунд после появления нового запроса

#### Scenario: Ожидающих запросов нет
- **WHEN** счётчик равен `0`
- **THEN** бейдж не отображается

### Requirement: Единая страница Access Management
Страница `/ui/{cluster}/access-management` SHALL быть единственной страницей функции и содержать заголовок «Access Management», кнопку «Request Prefix Access» и таблицу «My Requests» со всеми запросами текущего пользователя (цель, роль, статус, причина, причина отказа, кто решил, дата создания). Статусы MUST отображаться бейджами Pending, Approved, Rejected; цели-префиксы MUST помечаться бейджем «Prefix».

#### Scenario: Пользователь смотрит свои запросы
- **WHEN** пользователь открывает страницу Access Management
- **THEN** он видит таблицу My Requests со своими запросами в любом статусе, включая причину отказа для отклонённых

### Requirement: Секция управления для владельцев и суперадминов
Секция «Manage Accesses» SHALL отображаться, только если хотя бы один из ответов `requests/pending`, `requests/all` или `accesses` для текущего пользователя непуст. Секция MUST содержать вкладки: Pending (с бейджем количества, кнопками Approve и Reject; Reject открывает диалог с необязательной причиной), History (все запросы в зоне ответственности) и Current Accesses (кнопка Revoke с подтверждением). После любого действия UI SHALL показывать уведомление и перезагружать данные страницы.

#### Scenario: Владелец одобряет запрос из UI
- **WHEN** владелец на вкладке Pending нажимает Approve
- **THEN** появляется уведомление `Request approved`, запрос исчезает из Pending и отображается в History со статусом Approved

#### Scenario: Отзыв с подтверждением
- **WHEN** владелец нажимает Revoke на вкладке Current Accesses
- **THEN** показывается диалог подтверждения, и только после подтверждения выполняется `DELETE /accesses/{id}`

#### Scenario: Пользователь без зоны ответственности
- **WHEN** у пользователя пусты все три списка управления
- **THEN** секция Manage Accesses не отображается

### Requirement: Запрос доступа к префиксу из UI
Кнопка «Request Prefix Access» SHALL открывать диалог, в котором префикс выбирается из `GET /prefixes`, для выбранного префикса показываются его владельцы, роль выбирается из `requestableRoles`, причина необязательна. UI MUST блокировать отправку без выбранного префикса или роли с предупреждением; при ошибке сервера SHALL показывать сообщение сервера.

#### Scenario: Отправка запроса на префикс
- **WHEN** пользователь выбирает префикс `team-a\..*`, роль `READ` и нажимает Request
- **THEN** отправляется `POST /request` с `{prefix, role, reason}`, показывается `Prefix access request submitted`, таблица My Requests обновляется

#### Scenario: Роль не выбрана
- **WHEN** пользователь нажимает Request без выбранной роли
- **THEN** запрос не отправляется, показывается предупреждение `Please select a role`

### Requirement: Кнопка Request Access на странице топика
При включённой функции страница топика SHALL показывать кнопку «Request Access» рядом с заголовком независимо от текущих прав пользователя. Кнопка MUST открывать диалог, в котором показываются текущие роли пользователя для этого топика (только точечные доступы, из `my-access`), владельцы топика или предупреждение `Owner not assigned. The request will be reviewed by an administrator.`, обязательный выбор роли и необязательная причина.

#### Scenario: Топик с владельцем
- **WHEN** пользователь открывает диалог Request Access на топике `team-a.orders`, у префикса которого есть владельцы
- **THEN** в диалоге перечислены владельцы (имя и email), а отправка создаёт запрос `POST /request` с `{topicName, role, reason}`

#### Scenario: Топик без владельца
- **WHEN** имя топика не матчится ни одним `prefix-owners`
- **THEN** диалог показывает предупреждение, что запрос рассмотрит администратор, и всё равно позволяет отправить запрос

### Requirement: Обработка 401 и 403 в UI
UI MUST перенаправлять пользователя на страницу логина (с сохранением `returnTo`) только при ответе API `401`. При ответе `403` UI SHALL показывать предупреждение и оставлять пользователя на текущей странице залогиненным.

#### Scenario: Недостаточно прав
- **WHEN** залогиненный пользователь открывает раздел, к которому у него нет прав, и API отвечает `403`
- **THEN** показывается предупреждение, редиректа на логин нет

#### Scenario: Сессия истекла
- **WHEN** API отвечает `401`
- **THEN** UI перенаправляет на страницу логина

### Requirement: Обновление прав в UI без перелогина
Права, от которых зависит отображение элементов UI (например, вкладка Data на странице топика), SHALL загружаться из `GET /api/me` при инициализации приложения и MUST учитывать актуальные доступы из БД. Новые или отозванные доступы SHALL отражаться в UI после перезагрузки страницы без повторного входа.

#### Scenario: Доступ выдан во время сессии
- **WHEN** пользователю, не имевшему прав на данные топиков, одобрили `READ` к `team-a.orders`, и он перезагружает страницу в браузере
- **THEN** на странице топика `team-a.orders` доступна вкладка Data без повторного логина
