# Spec Delta

## MODIFIED Requirements

### Requirement: Одобрение запроса
Владелец цели или суперадмин SHALL одобрять запрос через `PUT /requests/{id}/approve`. Сервер MUST проверять по порядку: запрос существует (иначе `404`), пользователь — владелец цели или суперадмин (иначе `403`), статус `PENDING` (иначе `400`). При одобрении запрос SHALL получить статус `APPROVED`, `resolvedBy` и `resolvedAt`, и SHALL быть создан доступ (`topic_access`) с той же целью и ролью, `grantedBy` и ссылкой на запрос, если такого активного доступа ещё нет. Отозванный доступ MUST NOT считаться дубликатом активного.

#### Scenario: Владелец одобряет запрос
- **WHEN** владелец `team-a\..*` одобряет `PENDING`-запрос `alice` на `team-a.orders` с ролью `READ`
- **THEN** запрос переходит в `APPROVED`, а у `alice` появляется активный доступ `READ` к `team-a.orders`

#### Scenario: Повторное одобрение
- **WHEN** вызывается одобрение уже одобренного запроса
- **THEN** сервер отвечает `400` с сообщением `Request is not in PENDING status`

#### Scenario: Доступ уже существует
- **WHEN** одобряется запрос, для которого у пользователя уже есть активный доступ с той же целью и ролью
- **THEN** запрос переходит в `APPROVED`, дубликат активного доступа не создаётся

#### Scenario: Повторная выдача после отзыва
- **WHEN** у `alice` уже есть отозванный доступ `READ` к `team-a.orders` и одобряется её новый запрос на ту же цель и роль
- **THEN** создаётся новая активная запись, а прежняя запись сохраняется отозванной со своими `revokedBy` и `revokedAt`

#### Scenario: Несуществующий запрос
- **WHEN** вызывается одобрение по неизвестному `id`
- **THEN** сервер отвечает `404`

### Requirement: Просмотр и отзыв выданных доступов
Сервер SHALL предоставлять `GET /accesses` — активные и отозванные доступы в зоне ответственности пользователя (для суперадмина — все), и `DELETE /accesses/{id}` для отзыва. Отзыв MUST быть доступен только владельцу цели или суперадмину (иначе `403`), для неизвестного `id` — `404`. Отзыв SHALL сохранять запись, заполнять `revokedBy` и `revokedAt` и отвечать `200`; исходный запрос остаётся в статусе `APPROVED`.

#### Scenario: Владелец отзывает доступ
- **WHEN** владелец `team-a\..*` вызывает `DELETE /accesses/{id}` для активного доступа `alice` к `team-a.orders`
- **THEN** запись сохраняется с именем владельца в `revokedBy` и временем в `revokedAt`, а следующий запрос `alice` к данным `team-a.orders` получает `403`

#### Scenario: Отозванный доступ виден владельцу
- **WHEN** владелец вызывает `GET /accesses` после отзыва доступа в своей зоне ответственности
- **THEN** ответ содержит эту запись с данными выдачи и отзыва, включая `revokedBy` и `revokedAt`

#### Scenario: Повторный отзыв
- **WHEN** для уже отозванного доступа повторно вызывается `DELETE /accesses/{id}`
- **THEN** сервер отвечает `200`, а автор и время первого отзыва не изменяются

#### Scenario: Чужой доступ
- **WHEN** пользователь, не владеющий целью и не суперадмин, пытается отозвать доступ
- **THEN** сервер отвечает `403`, а запись не изменяется

### Requirement: Справочные эндпоинты
Сервер SHALL предоставлять любому аутентифицированному пользователю: `GET /prefixes` — список `{prefix, owners[{username, email}]}` из `prefix-owners`; `GET /topic/{topicName}/owners` — `{topicName, owners[]}` по всем префиксам, матчащим топик; `GET /topic/{topicName}/my-access` — активные доступы текущего пользователя, выданные точечно на этот топик. Доступы на префикс и отозванные доступы в `my-access` MUST NOT включаться.

#### Scenario: Владельцы топика
- **WHEN** пользователь вызывает `GET /topic/team-a.orders/owners`
- **THEN** ответ содержит владельцев всех `prefix-owners`, чей `prefix` матчит `team-a.orders`, или пустой список

#### Scenario: Доступ на префикс не виден в my-access
- **WHEN** у `alice` есть только доступ на префикс `team-a\..*` и она вызывает `GET /topic/team-a.orders/my-access`
- **THEN** ответ — пустой список

#### Scenario: Отозванный доступ не виден в my-access
- **WHEN** точечный доступ `alice` к `team-a.orders` отозван и она вызывает `GET /topic/team-a.orders/my-access`
- **THEN** ответ не содержит отозванную запись

### Requirement: Хранение запросов и доступов
Запросы и доступы MUST храниться в PostgreSQL в таблицах `access_request` и `topic_access`, схема создаётся миграциями Flyway (`V1__access_management.sql`, `V2__prefix_access.sql`, `V3__access_request_cluster_reminder.sql`, `V4__topic_access_revocation.sql`). У записи заполнено ровно одно из полей `topic_name` или `prefix`. Доступ активен при `revoked_at IS NULL`. Уникальность MUST действовать только среди активных записей по `(username, topic_name, role)` для топика и `(username, prefix, role)` для префикса. Запросы и отозванные доступы не удаляются.

#### Scenario: Доступ на топик и на префикс одновременно
- **WHEN** у `alice` есть доступ `READ` к `team-a.orders` и одобряется её запрос `READ` на префикс `team-a\..*`
- **THEN** в `topic_access` хранятся обе записи

#### Scenario: История нескольких циклов выдачи и отзыва
- **WHEN** одна и та же роль на одну цель дважды выдаётся и отзывается, затем выдаётся третий раз
- **THEN** в `topic_access` хранятся две отозванные записи и одна активная, а вторая активная запись для того же сочетания пользователя, цели и роли запрещена ограничением БД

### Requirement: Применение доступов через DatabaseClaimProvider
При включённой функции `DatabaseClaimProvider` SHALL быть основным (`@Primary`) `ClaimProvider`, оборачивающим `LocalSecurityClaimProvider`: к его группам добавляются динамические группы только по активным записям `topic_access` пользователя. Каждая активная запись MUST превращаться в группу с ролью `akhq-role` из `requestable-roles` по имени роли, кластерами `.*` и паттерном: для топика — точное имя (regex-литерал), для префикса — строка префикса как regex. Ключ группы MUST начинаться с `db-access-`. Отозванные записи MUST NOT создавать динамические группы.

#### Scenario: Доступ на топик даёт точное совпадение
- **WHEN** у `alice` активный доступ `READ` (`akhq-role: topic-data-read`) к `team-a.orders`
- **THEN** у неё есть группа с ролью `topic-data-read` только для топика `team-a.orders`, а топик `team-aXorders` ею не покрывается

#### Scenario: Доступ на префикс покрывает будущие топики
- **WHEN** у `alice` активный доступ `READ` на префикс `team-a\..*` и создаётся новый топик `team-a.payments`
- **THEN** `alice` может читать данные `team-a.payments` без нового запроса

#### Scenario: Отозванный доступ не даёт группу
- **WHEN** у `alice` есть только отозванная запись доступа к `team-a.orders`
- **THEN** динамическая группа для этой записи не создаётся

#### Scenario: Роль удалена из конфигурации
- **WHEN** роль активной записи доступа отсутствует в `requestable-roles`
- **THEN** запись пропускается с предупреждением в логе, группа не создаётся
