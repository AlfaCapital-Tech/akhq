# Design

## Context

`topic_access` сейчас хранит только действующие доступы: `DELETE /accesses/{id}` удаляет строку, а `DatabaseClaimProvider` и `my-access` читают все строки пользователя. При одобрении дубликат ищется по пользователю, цели и роли. Частичные unique-индексы V2 разрешают только одну строку для такого сочетания, поэтому после soft-delete они заблокируют повторную выдачу. Подробная мотивация — в `proposal.md`.

## Goals / Non-Goals

**Goals:**
- Сохранять каждый цикл выдачи и отзыва без участия отозванных записей в авторизации.
- Разрешить повторную выдачу новой строкой и гарантировать один активный доступ на сочетание пользователя, цели и роли.
- Сохранить автора и время первого отзыва, включая одновременные запросы к разным репликам.

**Non-Goals:**
- Восстановление ранее удалённой истории, причина отзыва, срок хранения и очистка истории.
- Отдельный endpoint или вкладка для истории, восстановление отозванной строки в активную.
- Изменение статуса исходного запроса после отзыва.

## Decisions

### Признак активности и точечные запросы
В `TopicAccessEntity` добавляются nullable `revokedBy` и `revokedAt`; активность — `revokedAt == null`, отдельный статус не нужен. `DatabaseClaimProvider`, `my-access` и поиск дубликата при Approve используют derived-запросы с `RevokedAtIsNull`. `GET /accesses` продолжает использовать `findAll()` и текущую ownership-фильтрацию, чтобы вернуть оба состояния.

Глобальный `@Where`/`@SQLRestriction` не применяется: он скрыл бы историю из `GET /accesses`. Новый DTO и endpoint не нужны — Micronaut Serde уже сериализует поля сущности.

### Миграция и повторная выдача
`V4__topic_access_revocation.sql` добавляет `revoked_by VARCHAR(255)` и `revoked_at TIMESTAMP`, удаляет два unique-индекса V2 и создаёт их заново с дополнительным условием `revoked_at IS NULL`. Существующие строки получают `NULL` и остаются активными.

При Approve учитывается только активный дубликат. Если есть лишь отозванная запись, создаётся новая строка с новым `id`, `grantedBy`, `grantedAt` и `requestId`; старая не реактивируется, иначе прежний отзыв стирался бы. Ограничения БД допускают один активный и любое число исторических доступов для топика и префикса.

### Первый отзыв выигрывает
После существующих проверок существования и владения контроллер вызывает условный `UPDATE ... WHERE id = :id AND revoked_at IS NULL`, по образцу атомарного захвата в `AccessRequestRepository`. Значения `revokedBy`/`revokedAt` устанавливаются только первому вызову. При результате `0` доступ уже отозван: возвращается `200`, уведомление повторно не отправляется, существующие значения не перезаписываются.

Это сохраняет идемпотентность DELETE и не требует нового состояния ошибки. Альтернатива «прочитать-проверить-обновить» оставляет гонку между репликами.

### UI
Current Accesses переименовывается в Accesses. Статус вычисляется из `revokedAt`: активная запись получает Active и Revoke, отозванная — Revoked, `revokedBy`, `revokedAt` и отсутствие кнопки. Состав остальных колонок и запросов не меняется; текст тура обновляется вслед за названием вкладки. Новые frontend-абстракции не нужны.

## Risks / Trade-offs

- Объём `GET /accesses` будет расти с историей → пока принимаем, поскольку endpoint уже возвращает полный список; пагинация потребуется при реальном росте данных.
- Пересоздание индексов кратковременно блокирует изменения `topic_access` → таблица небольшая, миграция выполняется штатно при старте.
- Старый backend после появления истории может прочитать несколько строк как `Optional` → откат приложения после soft-delete не выполняем без совместимой миграции/восстановления данных.

## Migration Plan

1. При старте новая версия применяет V4; ручного заполнения данных не требуется.
2. После выката проверить отзыв, отсутствие прав, отображение истории и повторную выдачу для топика и префикса.
3. Автоматический down-миграции нет: поля и историю не удаляем. До первого soft-delete достаточно откатить приложение; после него откат только на версию, понимающую историю, либо с восстановлением совместимого состояния БД.
