# Design

## Context

- Письмо собирает `NotificationService.notifyNewRequest` сразу после сохранения запроса; ссылка — `baseUrl + "/ui"`. Получатели — владельцы по `prefix-owners`, иначе суперадмины.
- `AccessRequestEntity` не хранит кластер: контроллер принимает `{cluster}` в пути, но при создании его не сохраняет. Доступы кластер-независимы (группы с `clusters: .*`), поэтому для авторизации кластер и не нужен — только для навигации по ссылке.
- Страница `/ui/:clusterId/access-management` уже грузит `requests/my`, `requests/pending`, `requests/all` (с фильтром по зоне ответственности) и `accesses`. Секция Manage Accesses показывается, если хоть один список непуст. Вкладка по умолчанию — Pending.
- Возврат после входа: при незалогиненном пользователе `AkhqRoutes._setCurrentUser` вызывает `Root.saveReturnToOnSessionExpiry`, который кладёт в `sessionStorage.returnTo` путь вместе с `search`; после SSO сервер редиректит на `/ui`, а маршрут `/ui` берёт `returnTo` (`checkAfterLoginAndHandleRedirect`). Тот же механизм на `401` в `api.jsx`. Тур онбординга уже использует query-параметр `?tour=1` на этой странице — приём проверенный.
- Планировщика в форке нет. Micronaut поддерживает `@Scheduled` с интервалами из конфигурации; значения вида `3d` парсятся в `Duration`. Helm-чарт позволяет `replicaCount > 1`, значит одно и то же задание может запускаться на нескольких репликах одновременно.
- Тесты access management идут на PostgreSQL через Testcontainers (`AbstractTestWithPostgres`), `EmailSender` создаётся со stub-хостом, отправка выключена.

## Goals / Non-Goals

**Goals:**
- Из письма — сразу на нужный запрос с кнопками, в нужном кластере, через SSO
- Решённый запрос по ссылке показывает статус, а не ошибку
- Напоминания по Pending-запросам с настраиваемым интервалом, без дублей при нескольких репликах, с остановкой после решения

**Non-Goals:**
- Approve/Reject прямо из письма (одноразовые ссылки с токеном) — см. альтернативы
- Письма заявителю об одобрении/отклонении — спека `access-notifications` их намеренно не шлёт
- Эскалация суперадминам после N напоминаний, лимит числа напоминаний
- Правки файлов upstream (`Table.jsx`, `AkhqRoutes.jsx`); выделение строки — через CSS `:has()` в коде форка

## Decisions

### Ссылка: существующая страница + query-параметр
Формат: `<base-url>/ui/<cluster>/access-management?request=<uuid>`. Маршрут существует, `returnTo` сохраняет `search`, новых маршрутов и дублирования страницы нет. Отдельный путь `/requests/<id>` отклонён: это вторая страница с теми же кнопками и свой маршрут под флагом.

### Кластер запроса хранится в записи
Новая колонка `cluster` в `access_request`, заполняется из `{cluster}` при `POST /request`. Для старых записей (`NULL`) в ссылке используется первый кластер из `akhq.connections`. Альтернатива «кластер по умолчанию в конфиге» отклонена: при нескольких кластерах лид попадёт не туда, а конфиг придётся держать согласованным с `connections`.

### Карточка запроса на странице, без нового эндпоинта
При `?request=<id>` страница после загрузки списков ищет запрос в `requests/all` (зона ответственности) и в `requests/my`. Выбирается вкладка Pending, над секциями рисуется карточка «Запрос из письма»: заявитель, цель, роль, причина, дата, статус.
- Pending и пользователь — согласующий (запрос найден в `requests/all`): кнопки Approve и Reject, те же обработчики, что в таблице
- Решённый: статус, кто и когда решил, причина отказа
- Не найден ни в одном списке: «Запрос не найден или вы не его согласующий», без тоста ошибки и без редиректа

Отдельный `GET /requests/{id}` не нужен: списки уже загружены и уже отфильтрованы по правам.

Строка запроса в таблице Pending тоже выделяется, без правки `Table.jsx` (upstream): в ячейке цели для нужной строки рендерится маркер `data-request-highlight`, а CSS форка красит родительскую строку через `tr:has([data-request-highlight])` и после загрузки прокручивает к ней (`scrollIntoView`). `:has()` поддерживают все актуальные браузеры; без поддержки остаётся карточка. Если кластер в ссылке неизвестен пользователю, `AkhqRoutes` сам подставит первый доступный — поведение upstream.

После Approve/Reject параметр остаётся в URL: перезагрузка покажет карточку со статусом, что и требуется.

### Возврат после SSO — проверка существующего механизма
По коду цепочка `saveReturnToOnSessionExpiry → /oauth/login → callback → /ui → returnTo` уже сохраняет путь с `search`. Решение: проверить вручную на стенде с OIDC; править только если сломано, и только в файлах форка или точечно.

### Напоминания: задание внутри приложения, захват через БД
Новый класс форка `AccessRequestReminderJob` с `@Scheduled(fixedDelay = …, initialDelay = …)`; тик — 15 минут (переопределяется служебным ключом `reminder-check-interval`, нужен для локальной проверки), интервал напоминания — `notifications.reminder-interval` (`Duration`, по умолчанию `3d`). При `enabled: false` или интервале `0` задание ничего не делает.

Алгоритм тика:
1. Выбрать `PENDING`, у которых `coalesce(last_reminded_at, created_at) <= now() - interval`
2. Для каждого выполнить `UPDATE access_request SET last_reminded_at = now() WHERE id = :id AND status = 'PENDING' AND coalesce(last_reminded_at, created_at) <= :threshold`
3. Если обновлена ровно одна строка — отправить письмо; иначе запрос уже решён или взят другой репликой

Так БД служит замком: реплики не шлют дубли, после рестарта отметка сохраняется, после Approve/Reject запрос выпадает из выборки. Ошибка SMTP не откатывает отметку: следующее напоминание уйдёт через интервал, как и у первого письма (ERROR в лог).

Письмо-напоминание: тема `<subject-prefix> Reminder: access request from <username> pending <N> days`, тело — как у первого письма плюс дата создания, ссылка та же. Получатели — те же, что у первого письма (пересчитываются на момент отправки: владельцы могли смениться в конфиге).

Отклонённые варианты: внешний CronJob/сервис, дергающий API, — новый деплой и служебная аутентификация ради одного запроса к БД; лидер-выборы или advisory lock — лишняя механика, условного UPDATE достаточно.

### Миграция
`V3__access_request_cluster_reminder.sql`: `ALTER TABLE access_request ADD COLUMN cluster VARCHAR(255), ADD COLUMN last_reminded_at TIMESTAMP`. Индекс `idx_access_request_status` уже есть; выборка по статусу небольшая, отдельный индекс не нужен.

## Risks / Trade-offs

- После первого выката с `reminder-interval > 0` все давно висящие Pending-запросы получат напоминание в первый же тик → это ожидаемо, предупредить владельцев в анонсе релиза
- Списки `requests/all` грузятся целиком (`findAll`) — карточка опирается на них; при росте таблицы это общая проблема страницы, не этой задачи
- Поведение `returnTo` при SSO проверяется только вручную: автотеста OIDC-цепочки нет → ручной сценарий в tasks
- Часы реплик могут расходиться → порог и отметка считаются на JVM реплики, которая захватила запрос; расхождение в секунды на интервалах в дни несущественно
- Письмо-напоминание уходит владельцам, а не заявителю: заявитель по-прежнему видит статус только на странице
