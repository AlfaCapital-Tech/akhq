# Design

## Где считать согласующих

На сервере, в контроллере: правило «владельцы префикса, иначе суперадмины» уже есть в `NotificationService` для адресатов писем, и клиенту его дублировать не нужно (матчинг регулярок префиксов и список суперадминов клиенту недоступны). Поле `approvers` заполняется только для собственных запросов пользователя (`/requests/my`, ответ на `POST /requests`); в списках согласующего (`/requests/pending`, `/requests/all`) оно `null`, там владелец и так знает, что это он.

## Почему `@Transient` поле, а не отдельный DTO

Клиент читает поля запроса по именам сущности (`topicName`, `role`, `status`, …). Обёртка потребовала бы дублировать все поля или менять клиент целиком. Вычисляемое поле на сущности, помеченное `@Transient`, Hibernate не трогает, Micronaut Serde сериализует. Для префиксного запроса владельцы берутся по точному совпадению префикса, для топика — по регулярке, как и в письмах.

## UI

Колонка Approvers в My Requests: имена через запятую, каждое — `mailto:` на e-mail владельца, при отсутствии e-mail — просто имя. В карточке заявителя та же разметка в строке «Waiting for the decision of: …». Пустой список невозможен при настроенных суперадминах; на всякий случай показывается «-».
